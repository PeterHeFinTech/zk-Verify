# zk-Verify

Research prototype for three bounded zero-knowledge compliance statements. It contains a React interface, Circom circuits, local input preparation, and a script that generates Groth16 proving artifacts and Solidity verifiers. No customer data, sanctions list, financial figures, credentials, proof artifacts, or deployed contracts are bundled.

## Status

The code is scaffolded but dependencies are **not installed** and the circuits have **not been compiled or benchmarked** on this computer. No claim of regulatory approval is made. The private input generator and proof interface require installation and validation before use. See `docs/methodology.md` for the precise statements and limits.

## Project layout

| Path | Purpose |
|---|---|
| `src/` | Browser interface; generates and verifies proofs locally with `snarkjs` |
| `circuits/kyc.circom` | Membership and validity of an issuer-approved credential |
| `circuits/aml.circom` | Bounded exact-match set disjointness |
| `circuits/solvency.circom` | Bounded comparison of committed assets and liabilities |
| `scripts/prepare-input.mjs` | Validates supplied JSON and computes Poseidon commitments |
| `scripts/prepare-circuits.sh` | Compiles circuits and creates development proving artifacts |
| `contracts/` | Solidity verifiers generated by the setup script; no deployment included |

## When you decide to install dependencies

The following is documentation, not a record of commands run:

1. Install the Circom 2 compiler. The circuits declare `pragma circom 2.1.6`, so use Circom 2.1.6 or a compatible newer release.
2. Install `snarkjs` CLI.
3. From this directory run `npm install`, which provides React, Vite, `snarkjs`, `circomlib`, and `circomlibjs`.
4. Run `bash scripts/prepare-circuits.sh`. This performs a **local development setup**, not a production trusted setup. Its output includes large `.zkey` files and Solidity verifier source.
5. Prepare your own input JSON with `node scripts/prepare-input.mjs <module> <source.json> <private-input.json>`.
6. Run `npm run dev`, open the local Vite URL, choose a module, load its `circuit.wasm`, `proving_key.zkey`, and `verification_key.json` from `public/artifacts/<module>/`, then load the private input JSON and generate a proof.

The private input and generated proof stay in the browser unless you explicitly download them. The application does not call an API or transmit input data. Google Fonts are loaded from the network when available; replace them with local fonts if fully offline operation is required.

## Source input formats

All numeric values should be JSON strings containing non-negative decimal integers. No source data is included. The helper refuses to overwrite an existing output file.
Keep any sensitive source and generated input files under `data/`, which is ignored by Git.

### KYC

The input file contains `credentials` (1–8 objects), `selectedIndex` (zero-based), and `currentDay` (days since Unix epoch). Each credential has `secret`, `verified` (`1` for an approved credential), and `expiryDay` (days since Unix epoch). The helper computes a three-level Merkle root and path. The trusted issuer must independently control and publish the accepted root. A prover should not be allowed to choose an arbitrary root.

### AML screening

The input file contains `customers` and `watchlist`, each an array of 1–8 pre-normalised field integers. The helper pads unused slots with zero and computes Poseidon commitments. Exact equality is the only matching rule. A watchlist authority must independently publish the accepted watchlist commitment; otherwise a prover could choose a harmless list. A production system also needs sound identifier normalisation, source authentication, versioning, and dataset completeness controls.

### Solvency

The input file contains `assets` and `liabilities`, each an array of 1–8 integer values in the same smallest currency unit. Individual values must be less than 2^32. The circuit compares their sums and binds both eight-slot vectors to public Poseidon commitments. An external audit must establish asset ownership, valuation, and complete liabilities.

## Important security limits

- The AML circuit uses 64 equality comparisons. It is a bounded exact-match proof; it is **not** a cryptographic private set intersection protocol.
- Low-entropy customer identifiers and financial amounts may be vulnerable to guessing from unsalted public commitments. Do not put sensitive production data in this prototype.
- The KYC circuit establishes membership under a supplied root; it does not verify issuer signatures, root provenance, revocation, or credential holder binding.
- The solvency circuit does not establish whether data was omitted or whether a claimed asset is controlled by the prover.
- The setup script performs only one local contribution. Its keys must not be represented as suitable for a production trusted setup.
- No smart contract is deployed. The generated Solidity verifiers would verify mathematical statements only; application-level authorisation, freshness, and root registry would still be needed.

## Evaluation plan

After the toolchain is installed, first confirm compilation and valid/invalid witness behaviour. Record constraint counts, witness and proof generation time, verification time, proof size, and memory use for each fixed-size circuit. Varying data volume requires separate circuit configurations or redesigned dynamic bounds; this initial version supports at most eight entries per list.
